# 拾途杭州 · 当前范围与下一阶段执行计划

版本：v1.1；确认日期：2026-11-04。本文为当前执行范围。原 product-outline.md 保留为历史设计基线。下文明确区分已实现功能与目标，不将规划中的能力描述为已交付。

## 产品定位

面向杭州 1—3 日短途游，帮助个人把必去地点、兴趣与时间条件变成可以在地图上编辑的行程。对外名称为“拾途杭州”，TripCanvas 保留为英文项目代号。

首版支持步行和驾车；用户确认具体地点、日期与必要条件。初始内容可以围绕西湖慢游、展馆与雨天、校园与城市漫步等主题组织，同时保留真实地点搜索，不限制为固定热门景点。资料不足的开放、预约、票价和入口信息明确为待确认。

当前外部搜索仍使用杭州周边经纬度框，可能返回邻近城市地点；按杭州行政区精确筛选尚待实现。跨城交通由用户提供到达和返程条件。其他城市、公交地铁、实时路况和票务不属于这轮交付。

## 当前真实状态

- 已有：地图与时间轴、真实地点搜索与消歧、动态地点加入和道路核验、步行 / 驾车、候选集合分日草案、修改预览、锁定与返程保护、停留协调、保存、版本恢复与可撤销分享接口。
- 已有模型分日排序与局部编辑；基础地点输入和部分常用调整使用明确的规则与排程计算，不等同于任意自由对话。
- 尚未完成：完整多条件需求理解、主动候选推荐、从一句话可靠生成完整行程、三套完整方案比较、游玩舒适度约束、统一后端规划事务与真实阶段事件、任务评测与完整面试交付。
- 本次定位收口不提升功能成熟度评级；后续按真实验收结果更新。

## 下一阶段，按顺序交付

### M1：一句需求到完整初稿（首先实现）

输入示例：

> 2026-11-14 去杭州两天，两个人，想去西湖和浙工大，喜欢咖啡，少走路，第二天 17:00 前到杭州东站。

交付链路：结构化需求 → 必要补充与地点消歧 → 确认必去集合 → 补充兴趣候选 → 分配日期和顺序 → 核验道路及约束 → 完整初稿 → 确认保存。

验收标准：

1. 一次输入能保留多个地点、人数、天数、兴趣、交通和返程条件，不忽略后半句。
2. “西湖”等区域和“浙工大”等多校区地点由用户确认具体位置，不凭空猜入口或校区；缺日期、车站等关键条件时集中补充。
3. 用户确认后生成完整 1—3 日初稿，不要求逐个追加地点来拼出计划。
4. 必去地点必须保留；无法全部满足时解释取舍，确认后才删减。
5. 全程路线和返程要求经过程序检查，未知路线不得标记通过。
6. 保存、刷新、继续编辑和恢复均能完整保留本次初稿。

### M2：路线质量与方案比较

在 M1 跑通后，同一确认需求生成少走路、轻松游、必去优先等不同方案，展示地点、交通用时、步行距离、停留与取舍。

必须先补充每日步行预算、停留建议范围、休息用餐等软约束。超限时提供减少地点或改变交通方式的备选供确认；不能只靠把所有停留压到 30 分钟来宣称方案合理。不承诺全局最优，不提供未计算的综合分数。

不同方案至少在地点集合、访问顺序、日间分配或停留安排上有实质区别；固定返程和用户选定必去条件应保持。

### M3：统一后端规划与运行记录

将规划、约束与最终确认的权威判断收敛到后端，前端专注预览和编辑。统一自然语言输入、规则与模型结果的结构；记录生成、数据查询、路线核验、排程和校验的真实运行阶段。模型提出偏好与活动操作，程序负责地点来源、道路时间与硬条件。

保留版本并发检查、幂等与失败草案；任务重启、超时和外部服务失败有明确状态。城市常量可封装为配置，但本轮不新增其他城市。

### M4：评测与求职交付

建立约 30 条固定任务，包含多地点、同名校区、雨天、晚出发、必去保护、返程冲突、不可满足条件和外部接口失败。分别记录理解正确、计划生成成功、必去与锁定遵循、错误接受、端到端耗时及模型调用量，不能用全部拒绝换取高遵循率。

完成完整线上用户流程验收、面试官可访问的体验入口、最终架构和 API 文档、90 秒视频及真实简历描述。修改访问权限需另按用户明确指示处理。

## 本轮验收优先级

先交付一份完整、可修改、可保存的杭州计划，再做多方案。阶段状态、评测及交付材料与真实完成情况同步。已有地图、账号、版本和分享能力继续复用。

M1 的首项具体工作：定义并实现统一的多地点需求结构与解析接口，将现有的单地点追加入口和候选草案入口接入同一套需求，不先扩展新城市或堆叠更多页面。
