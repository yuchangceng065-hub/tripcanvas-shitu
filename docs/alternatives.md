# 主动协调与多方案比较

## 用户流程

新建旅行 → 确认需求 → 搜索/确认候选 → 默认必去，按需勾选可选 → “生成多方案 · 主动协调” → 对比与切换预览 → 确认保存。

展示最多三套：少走路优先转场步行公里、充分游览优先保留地点与游览时长、轻松休闲优先降低单日活动和转场负担。可能得到相同路线但不同停留安排，界面会明确说明；完全相同的分日、顺序和停留自动合并。不会为了显示三套而改名复制，也不会展示仍有硬冲突的方案。

每套展示转场步行、完整交通接驳用时、游览停留、可支配空余、每日顺序、舍弃可选地点和查询时间。空余为每日时间窗扣除活动、起终点停留和转场后的剩余时间，包含固定活动前等待，不代表已经安排餐厅或休息。景点内部步行、入场、排队、营业/预约仍待确认。自驾保留“车辆初始在首站停车点”的既有假设，未确认停车点会提示。

## 算法与边界

`POST /api/v1/planner/alternatives` 接收已确认的候选、可选子集和需求。选择模型时仅调用一次模型生成完整种子排序；之后采用确定性局部搜索，不为每个分支调用模型。规则模式同样可用。

- 每个画像维护独立前沿，交错搜索，共享完整整日路线结果。
- 操作包含同日移动、跨日分配、移除/恢复可选地点。起点与固定返程作为锚点，不参与这些移动。
- 经纬度仅用于候选搜索排序，不作为公开指标或可行性结论。高德排序前统一到 GCJ-02。
- 完整整日路线保留自驾车辆连续性，不能把独立两点路线拼成车辆可瞬移的结果。
- 停留可在当前地点建议时长的保守下限内缩短（约六成并按 15 分钟取整，至少 30 分钟），不压缩固定安排；仍不可行时继续尝试重排、跨日和可选取舍。
- 单次最多 24 个完整候选评估、12 次整日路线查询、65 秒搜索时间。种子模型与坐标准备在搜索前，各有既有上游超时。限制的是整日路线请求，内部高德请求仍受持久化供应商预算控制。
- 原有供应商预算/限速不变；收到全局 429/502/503 时不反复请求。不可达候选可换顺序继续；时间或数量上限到达后仅返回已完整核验结果。
- 这是有界启发式搜索，不保证全局最优，也不能用有限搜索未找到来证明数学上无解。无可行结果时提供待调整草案/失败原因，不把未知道路当零分钟。

## 数据与确认

必去集合保存在 `requirements.mustVisitIds`，相应活动为 keep，跨方案保留稳定活动 ID。确认重新算路，并检查必去守恒、固定预约、返程、时间范围和步行预算。已保存的必去集合不能通过普通方案确认静默解除。

比较与切换不写旅行或版本，选定后沿用 `/planner/confirm`。保存后的手工编辑仍可作为草稿；其他编辑入口的全面统一不在本次新增范围。备选集合当前保留在新建向导内，选定旅行保存到云端；尚无跨会话长期保留整个比较集合的分支库。

## 验证

- （历史快照）前端 76 项、后端 101 项测试和构建通过；当前数字见 README「当前状态」段。
- 自动化覆盖：真实道路耗时决定换序、跨日救回过满初稿、必去不可删、停留下限、固定返程、指标汇总、重复方案合并、步行预算未知、配额与超时、预览切换无写入、最终确认保存。
- 本地浏览器使用隔离 SQLite + 真实 OSRM：曲院风荷和孤山馆区必去，浙江美术馆和雷峰塔可选，生成三套不同方案。少走路 1.9 km / 26 分钟 / 游览 120 分钟；充分游览 6.5 km / 88 分钟 / 游览 360 分钟；轻松休闲 1.9 km / 26 分钟 / 游览 180 分钟。选择充分游览、确认保存、刷新后时间与地点一致。这些是本次查询的样例，不是所有输入的性能或质量保证。

线上已用真实 Groq 与高德验证相同流程，返回三套不同方案，指标与高德分段逐项汇总一致；选中后确认保存、重新打开一致。样例与边界见 verification.md。
